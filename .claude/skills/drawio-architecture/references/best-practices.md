# 構成図のベストプラクティス

このスキルが従う規則のまとめ。構成図のレビュー依頼のときに読む(作図のたびには読まない。作図に必要な規則は SKILL.md に要約済み)。
`[自動]` はスクリプトの検査(`[BP]` 警告)やレイアウトで自動的に担保されるもの、
`[設計]` は仕様ファイルを書くときに判断して守るもの。

出典:
- Microsoft「Azure architecture icons」の利用上の注意(Do / Don't): https://learn.microsoft.com/azure/architecture/icons/
- AWS Architecture Icons の利用ガイドと、それを解説した「AWS Architecture Diagrams Guidelines」: https://dev.to/aws-builders/aws-architecture-diagrams-guidelines-595d
- C4 model「Notation」のチェックリスト: https://c4model.com/diagrams/notation

## 1. 図の目的と範囲

- [設計] 描き始める前に「誰に・何を伝える図か」を決める。読み手(運用担当、セキュリティ審査、顧客など)によって描く範囲が変わる。
- [設計] 1枚に描く流れは1〜2本にする。全リソース・全通信を1枚に詰め込まず、全体図と観点別の図(ネットワーク、監視・ログ、運用アクセス、DR など)に分ける。
  - [自動] ノード25個超・矢印20本超で分割を促す警告が出る。
- [設計] 少なくとも本番環境の図を作る。ほかの環境は差分だけ説明すればよい。
- [設計] 論理構成(役割の関係)を説明する図にはクラウドのアイコンを使わず、`icon: box` の四角で描く。クラウドのアイコンは物理構成・配置を表す図で使う。

## 2. タイトルと凡例

- [自動] タイトル(`title`)を必ず付ける。「システム名 + 環境 + 図の観点」を含める(例: 〇〇システム 本番環境 ネットワーク構成図)。
- [自動] 凡例を付ける。矢印の色・線種の意味を、読み手が慣習を知らなくても分かるように示す。
- [設計] 略語(PE、NSG、AGW など)は読み手が知らない可能性があれば、ラベルで正式名を併記するか凡例で説明する。
- [設計] 説明文なしで図だけを見て大筋が分かるかを確認する。

## 3. アイコン

- [自動] 公式のアイコン(draw.io 同梱の Azure / AWS 公式アイコン)を使う。切り抜き・反転・回転・変形・色の変更をしない。
- [自動] アイコンの近くに製品名・リソース名を書く(ラベル未指定は警告)。
- [設計] 同じ種類のリソースには常に同じアイコンを使う。新旧のアイコンセットを混ぜない。
- [設計] 公式アイコンを自社の製品やサービスを表すために使わない。自社のシステムは `icon: box` で描く。

## 4. 境界(グループ)と配置

- [設計] 外側から「クラウド/アカウント(サブスクリプション) → リージョン → ネットワーク(VNet/VPC) → サブネット」の順に入れ子にする。
- [自動] AWS はアカウント境界(`aws.account` または `aws.cloud`)を描く。単一アカウントでも描く。複数アカウントの場合は、関係するアカウントだけを描く。
- [自動] グローバルサービス(CloudFront、Route 53、IAM など)はリージョンの外、アカウントの中に置く。
- [自動] リージョナルサービス(S3、CloudWatch など)は VPC の外、リージョンの中に置く。VPC からの閉域接続は VPC エンドポイントで表す。
- [自動] AWS で NAT Gateway からインターネットへ出る構成では、VPC に Internet Gateway を描き、NAT Gateway → Internet Gateway の経路を示す。
- [自動] Azure の PaaS(Key Vault、Storage、ACR、Log Analytics など)は VNet の外に置く。閉域接続はサブネット内のプライベートエンドポイントで表す。VNet に直接配置されるもの(VM、AKS、App Gateway、Firewall、Bastion など)だけをサブネット内に置く。
- [設計] 関連するリソースのまとまり(例: 複数の関数)は `generic.box`(破線の枠)で囲む。
- [設計] パブリックサブネットとプライベートサブネットは色で区別する(AWS のグループ型は慣習どおり緑と青)。ただし、読み手がこの慣習を知らない前提で、サブネット名にも公開/非公開が分かる名前を付ける。

## 5. 矢印

- [自動] 線は水平・垂直だけで描き、アイコンや文字の上を通さない。交差するときはジャンプ(弧)で示す。
- [設計] 矢印の向きは通信を開始する側から受ける側へ(リクエストの方向)。1本の矢印は1方向の関係を表す。
- [設計] 戻りの通信は描かない。どうしても描く場合は破線にする。両方向の矢印(`a <> b`)は VPN トンネルなど、本当に双方向の接続に限る。
- [自動] すべての矢印にラベルを付ける。プロトコル/ポート(「HTTPS 443」)か、具体的な目的(「アクセスログ転送」)を書く。「通信」「接続」「使用」のようなあいまいな1語は警告される。
- [自動] 主要な処理の流れには `step` で番号を振る。番号は丸数字で矢印に表示され、図の下に「処理の流れ」として `desc` の説明が並ぶ。番号の重複や欠番は警告される。
- [自動] 矢印の種類は、色だけでなく線種(実線・破線・点線)や太さでも区別する。白黒印刷や色覚の多様性を考慮するため。

## 6. 色

- [設計] 色の使い方は図の中でも、複数の図の間でも統一する(同じ `kind` は同じ意味で使う)。
- [設計] 色を増やしすぎない。矢印の種類は5〜6種類までが目安。

## 7. 保守

- [設計] 仕様ファイル(YAML/JSON)をリポジトリで管理し、構成を変えたら同じ変更で図も更新する。
- [設計] 図はレビューを受ける。レビュアーからの質問が多い図は、描き方を見直す。
